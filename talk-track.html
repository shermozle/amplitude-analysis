How to use this

A floor, not a script. The prose is here so you don't lose the thread while eight people are asking why their chart is empty. Use your own words.

The hour is over-subscribed on purpose, because the room will talk. Blocks 15 and 16 are marked cut first and block 12 cut second. Shed those rather than eating into block 18, which needs the room and can't be made up afterwards.

Frame

Slides 1–4 · 5 minutes · ends at 5:00

10:00Cover

Right, laptops open. Today you do the work and I get out of the way, mostly.

Three parts. First the tools you use when you don't trust a number, because you're going to need them within about ten minutes. Then four chart types. Then the last stretch is yours: you each pick a question you currently answer in Adobe, and you build it.

Do

Don't linger here. Every second on the cover is a second not spent finding out that someone's login doesn't work.

21:00Where we are

Session one was the model, session two was events and properties. Today is analysis, which is where those two start paying for themselves.

One thing to flag: a decent chunk of today is about how charts mislead you. The data in this sandbox has several real problems in it, deliberately, so you'll get some practice at spotting them.

32:00What you need open

Three tabs and an extension. The handout, the sandbox, the demo site, and the Amplitude Event Explorer extension from the Chrome store. The handout has the link to it.

Every exercise is written out in the handout, with a "done when" line on each, so you can work at your own pace and you don't have to keep up with me.

Install the extension if you can, it takes about two minutes. If you'd rather not, exercise 2 works without it using the site's own event log.

One warning about the site. There's a demo panel behind the gear button, bottom right, and it has an API key field in it. If you paste anything in there your events go to a project I can't see and you'll spend the hour wondering why your charts are empty. Leave it alone.

Do

Wait for actual confirmation from every person. Ask by name if you have to. This is the cheapest thirty seconds in the hour.

If someone's login is broken, pair them with a neighbour immediately rather than trying to fix it. You can sort it out afterwards.

Chase the login, not the extension. A Chrome install can take longer than you'd think on a managed laptop, and nothing in the hour is blocked without it. If two or three people can't install it, say so out loud and move on, then make sure you demo the extension properly on the shared screen in block 7.

43:30One project, two sources

Before anything else, this. One project, two sources of data.

There's about a month of generated history, so that charts have something in them before any of us touches anything. And there's the live site, which is running the browser SDK with autocapture and Session Replay on. Anything you click in the next hour lands in the same project within a few seconds.

The important bit: the two sources use the same event and property names, but not the same contents. Nineteen events have history behind them. The other twenty-one are live only, so they'll look completely empty until someone uses the site.

Almost every strange number you meet today comes back to that. So before you assume a chart is broken, ask which sources feed it.

Worth saying out loud

This audience has spent years reconciling report suites, so the idea of two data sources meeting in one place with different semantics is entirely familiar to them. Lean on that rather than explaining it as if it were novel.

The toolkit

Slides 5–9 · 10 minutes · ends at 15:00

55:00Act 1 divider

We're starting with the debugging tools, which is back to front for a training session. The reason is that I want the charts you build later to be reading data you made yourself, and I want you to have seen it arrive.

65:15Exercise · make some data

Three minutes. Buy a phone.

One instruction that matters: stay logged out. While you're anonymous your device ID is yours alone, which makes you findable in a minute. I'll come back to why that matters.

Pick a mobile on a plan, choose a colour and a storage size, pick a plan, add it to the cart. In the cart, apply the promo code ONLINE50. Then check out: four steps, put whatever you like in the form fields.

Do

Do it yourself on the shared screen at the same time, slightly ahead, so anyone lost can follow along by watching.

Then ask the room to name three events they think they just sent. You'll get Add to Cart and something purchase-shaped. Nobody will guess the colour and storage selections, and that's the useful part: a well-instrumented configurator sends a lot more than people expect.

Keep an eye on

If someone's events aren't appearing at all later, the first thing to check is the Guides & Surveys toggle in their demo panel. It's wired to the SDK's opt-out flag, so switching it off stops everything, silently, including replay. It's a genuine mislabelling. Show it on purpose if you have a spare minute.

78:30What left the browser

Tool one. Event Explorer is a Chrome extension that sits in the page and lists every event as it's sent, with the full property payload, plus your device ID and session ID. If you've used the Experience Platform debugger or watched a packet monitor, this is that job.

If you haven't got the extension, the site has its own log: gear button, bottom right, or Ctrl+Shift+D. It records every tracking call the site makes. That's a good pattern to steal for their own build, because it costs about ten lines and saves hours.

Find your Order Placed and open up the Products property. One object per line item: brand, department, price, quantity, and a discount flag. That array is what makes the cart breakdowns in the next section possible, and it's the thing we spent most of session two on.

Do

Show the payload on screen rather than describing it. Point at discount_applied being Yes and ask why. The promo code is the answer, and it plants the flag for the typo you'll hit in block 12.

811:00What Amplitude accepted

Tool two, and this one's inside Amplitude, under Data. The Ingestion Debugger is a live view of events arriving at the server, with the payload as received.

Why that's a separate tool from the last one: the extension tells you what left the browser. This tells you what Amplitude kept. Those are different questions, and the gap between them is where a whole class of bug hides. Instrumentation that looks perfect in the browser and produces nothing in a chart is almost always a filter, a block, or a type mismatch, and this is the only place it shows.

Do

Ask the question on the slide and actually wait: if the extension shows the event and this doesn't, where do you look? Somebody will say the SDK key. Somebody will say a filter. Both are good answers and the discussion is worth more than my telling them.

912:30One user's actual events

Tool three, and it's the one you'll use most often. User Lookup gives you one person's events in order, with every property, and every user-property change marked at the point it happened.

It's what you open when someone says the report is wrong. You stop arguing about the aggregate and go and look at one person's actual events.

Now do this. Search for user ID 2003964661. Then log in on the site, as anybody, any email, and look again.

Everyone who logs in becomes that ID, because the site hardcodes one customer number. Eight people's sessions, one user profile, no error, no warning, and a chart of "purchases per user" that is quietly nonsense. That's the shape of a real bug, and it's the opening case in session four.

Don't oversell it

State it as a property of this demo site rather than a cautionary tale about anyone. It lands better, and it's true: this is a demo app someone wrote quickly, which is exactly how the real version of this bug gets written too.

Optional, 60 seconds

If you're ahead of the clock, find your own session in Session Replay from the user profile and play ten seconds of it. People tend to remember watching their own checkout back. Confirm before the day that replay is actually ingesting in this project.

Four charts

Slides 10–16 · 22 minutes · ends at 37:00

1015:00Act 2 divider

Four chart types. I'll build each one on the screen and you follow along. Shout if I'm going too fast, because I will be.

Do

Say the words "follow along on your own laptop" explicitly. Without it, half the room watches, and then block 18 starts from zero for them.

1115:15The four, and what they answer

Four questions, four chart types. How many broken down by what; where people fall out; what they did next; how often and for how long.

The third column is the route you'd take in Adobe for the same question, roughly. The fourth is where it actually differs, and you want to know those before you promise anyone parity.

One adjustment I'd flag now. Amplitude asks you to choose the question type before it gives you a canvas, which after years of starting from a blank freeform table feels like a constraint. Mostly it isn't: because the chart knows what you're asking, the controls in front of you are the ones that question needs. But it does mean the first move is deciding what kind of question you have.

Expect pushback here

Somebody will ask where the freeform table went. Data Table is the honest answer, and it's genuinely not a like-for-like replacement. Say that plainly rather than defending it, and note the specific thing they'd lose so it can go on the list for session 5.

1217:30When a number looks wrong

Four things in this data that will make you think something's broken. I'm giving you them up front so that when you hit one, you recognise it instead of losing five minutes.

One. There's a property spelled dicount_applied, missing an S. The generator spells it that way and the site spells it correctly, so the tracking plan shows two children under the same parent, each populated for about half the data. Group by either one and you've silently reported on half your cohort. Nothing errors.

Two. Group cart events by brand over thirty days and you'll see Fossil and Michael Kors sitting next to iPhones. The generated line items carry a fashion catalogue that can't be configured out. Scope the same chart to today and it resolves. That's two sources agreeing on a schema and disagreeing on contents, which looks exactly like a data quality incident.

Three. Autocapture sends its own page view event, and the site also sends a custom one with more properties. Two near-identical names next to each other in the picker. Neither is wrong, and someone in a hurry will pick the wrong one.

Four. Twenty-one events have no history at all. You'll hit that in about five minutes.

So: when a number surprises you, first question is which sources feed it, second is which of those four it is.

Cut second

If you're behind, cover the typo and the live-only events and skip the other two, then leave the slide up while they work. The typo is the one with the most transferable lesson, and the brands one explains itself the moment somebody hits it.

Do

On the typo, ask what they'd do about it two weeks after launch with a month of data behind it. Renaming in Data changes the display name going forward and doesn't rewrite what's ingested; a transformation can map old onto new; or you fix the emitter and document the seam. All three are defensible. It's a good two-minute argument and this room will have opinions.

1320:00Exercise · Data Table

Data Table first, because it's where you'll spend most of your time. New chart, Data Table. Rows: add to cart, checkout started, order placed.

Add a second metric so you've got uniques and totals side by side, and look at where they diverge. That gap is people doing the same thing more than once, and in a cart it's usually interesting.

Then break down by Products.department. Mobile, Internet, Accessories. This is the part that needed the array: you're grouping by something inside the cart rather than something about the cart as a whole.

Last, add a segment for Gold and VIP tier members.

Do

Ask the question on the slide: what would you build in a freeform table that you can't see a way to build here? Write the answers down. This is the first real input into the requirements list and it's better coming from them than from me.

1425:00Exercise · Funnel

Funnel. Product viewed, add to cart, checkout started, order placed.

First thing to play with: the conversion window. Move it from one day to thirty and watch the rate change. Same data, different question, and it's an explicit control rather than a property of how the report was built. That's one of the places your numbers will not line up with Adobe, and it's better to know why now than to discover it in a reconciliation meeting.

Group by department. Then insert checkout step completed as step four and watch the whole funnel fall over.

That event is live only. It has no generated history, so a funnel containing it reports only on people who have every single step, which right now is the handful of us in this room. A funnel silently narrows to whoever qualifies, and it doesn't tell you it's done it.

Do

Let them discover the collapse rather than announcing it. Wait for someone to say "mine's broken", then take the explanation from there.

Then ask where this bites while two tools are running side by side and half the events are live in one and half in the other. They know the answer better than you do.

1530:30Exercise · Journeys

Journeys, quickly. New chart, Journeys, start from address checked, then filter it to the cases where serviceability failed.

Read the branches. Where do people go when the answer is no? Support, another address, or away.

The starting point is what makes it work. A flow report anchored on page URLs can't ask this question, because "the address failed" isn't a page, it's a property value on an event.

Cut first

If you're past 32 minutes, stop running this as an exercise and just build it on the screen in ninety seconds while they watch. Demonstrating it teaches nearly as well, and shortening block 18 doesn't work at all.

1633:30Exercise · User Sessions

Last one, and it's quick. User Sessions: sessions per user, average session length. Add a second series segmented to people who placed an order, and compare.

One definitional thing. A session here is a gap of inactivity, set once as a project setting. It isn't a hit-based visit. So sessions and visits are close cousins rather than the same measure, and if you're reconciling the two tools, that's another line in the "expected to differ" column.

Cut first

Same as block 15. Demo it in a minute, or skip it entirely and mention that it exists. Of the four, this is the one they'll need least in week one.

One question each, one chart each.

Before you touch Amplitude, write the question down in one sentence. Something you actually get asked in Adobe. Two minutes on that, and do it properly, because a vague question produces a vague chart and you'll spend ten minutes discovering that.

Questions to expect

And which ones to take away rather than answer live

They askAnswer
Where's the freeform table? Data Table is the nearest thing, and it isn't like for like. Be specific about what's genuinely different rather than defending it, and get the missing capability onto the list.
Can we do calculated metrics? There are formula metrics in the segmentation and table charts. If someone names a specific Adobe calculated metric they need replicated, write it down and take it away. Guessing live here is how you end up wrong in front of the room.
Why don't these numbers match Adobe? Several legitimate reasons, and you can name three today: the conversion window is explicit, sessions are an inactivity gap rather than a hit-based visit, and the two sources in this sandbox have different coverage. Don't promise parity.
Why isn't property X in the dropdown? Usually one of three things: it's live only and there's no data in the window, the array hasn't been split, or it's the scope question from session 2. Check the window first, it's the common case.
Can we get hit-level data out? Yes, through the export API and the warehouse sync. That's session 4 territory, so park it.
Is there a virtual report suite equivalent? Not as a single feature. Depending on what they used it for the answer is saved segments, separate projects, or permissions. Ask what they used theirs for before answering.
Who can create charts, and can we stop them? Governance question, and a real one. Park it and bring it back properly rather than half-answering it at minute 55.

Pre-flight

The day before, in the sandbox, with the site open

The one that breaks everything

Confirm the Products property is split in this project, with type Array and item type Any. Splitting isn't retroactive for data already ingested, so if it's off, the cart breakdowns in blocks 7 and 13 have nothing to show and cannot be fixed on the day.

  • Every attendee has a working sandbox login. Check 48 hours ahead, not on the morning.
  • Pre-read sent: bring one question you answer in Adobe today, and install the Event Explorer extension.
  • Run one purchase yourself on the site and confirm the Products array arrives with all seven child properties.
  • Walk all four chart builds once, in this project, and correct any control names in the deck that have moved.
  • Confirm Journeys and User Sessions have enough data in this project to show something worth looking at.
  • Check what values the address check actually sends for its result property, so the block 15 filter matches.
  • Confirm Session Replay is ingesting in this project, not merely being sent by the site, before promising the optional replay moment in block 9.
  • Check the Guides & Surveys toggle is on in your own demo panel, and know where it is so you can check someone else's.
  • Have slide 19 reachable in one keystroke.
  • Decide now whether you're cutting blocks 15 and 16, based on how much block 12 ran over last time you taught something like it.
